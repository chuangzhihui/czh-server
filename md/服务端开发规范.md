## 2. 模块职责与依赖关系

父工程 `com.czh:czh` 聚合四个后端模块，依赖方向单向向下：

```
common  →  service  →  { admin, api }
```

| 模块 | artifactId | 职责 | 关键依赖 |
|---|---|---|---|
| **common** | `common` | 公共基础层：注解、全局配置、统一返回/异常、工具类 | web、security、mybatis-plus、redis、jwt、各类 OSS SDK |
| **service** | `service` | 数据服务层：实体、DAO、Service、DTO、VO | `common` |
| **admin** | `admin`（jar 名 `CZH_admin`） | 管理后台接口（**dev 18081 / test 8081 / prod 18093**）：Controller、Security 配置、切面 | `service` |
| **api** | `api`（jar 名 `CZH_api`） | 面向前端/App 的接口服务（**dev 8082 / test 8081 / prod 8081** ⚠️ test 与 prod 撞端口） | `service` |

> `czh-admin` 为**前端工程**（非 Maven 模块，React/TS/Vite），**不纳入本文档规范范围**，仅作为后端 `admin` 接口的对接方存在。

## 3. 分层架构与包约定

后端统一根包 `com.czh`。以 `service` 模块为例的目录约定：

```
com.czh.service
├── entity/        # 数据库实体（DO），与表一一对应
├── dao/           # MyBatis Mapper 接口（extends BaseMapper<T>）
│   └── xml/       # 自定义 SQL 的 Mapper.xml
├── service/       # 业务接口
│   └── impl/      # 业务实现（extends ServiceImpl<Dao, Entity>）
├── dto/           # 入参对象（按业务子包划分，如 admin/）
└── vo/            # 出参对象（按业务子包划分，如 admin/）
```

`admin` 模块约定：

```
com.czh.admin
├── controller/       # 【唯一放业务接口的地方】可自由增删改，无需评审
│   ├── admin/  role/  menu/  setting/  backup/  login/  common/
│   └── UploadController.java
├── framework/        # 【原 baseController/ 已重命名】只放框架基类与错误入口，改动需评审
│   ├── BaseController.java   # 8 个业务 Controller 的共同父类
│   └── ErrController.java    # /error 出口
├── config/           # SecurityConfig、LoggingAspect、CorsFilter
└── security/         # AdminDetails、JWTAuthFilter、AdminAuthFailedHandler 等
```

> **目录重构说明（架构师裁决「甲+」）**：历史上业务 Controller 与框架基类混在 `baseController/` 下，导致「不要修改 `baseController`」与「业务代码放 `controller/`」两条红线同时不可执行。现拆为 **`controller/`（业务，自由改）** 与 **`framework/`（框架，需评审）**。
> **为什么 `baseController/` 要改名而不是保留**：① 业务类写 `import com.czh.admin.baseController.BaseController` 语义别扭；② "baseController" 这名字本身是"业务控制器放这里"的语义残留，会诱导后来人继续往里塞。
> **迁移动作**见《现有后台改造清单》**批次 G**（8 个文件的机械移动、零逻辑改动）。

**调用链约定**：`Controller` → `Service/Impl` → `Dao(Mapper)` → `Entity`；入参一律走 `DTO`，出参一律走 `VO`。

## 4. 命名规范

| 维度 | 规范 | 示例 |
|---|---|---|
| 包名 | 全小写，根包 `com.czh` | `com.czh.service.dao` |
| 类/接口/方法/字段 | **驼峰命名**（CamelCase） | `AdminServiceImpl`、`getAdminList` |
| 数据库表名 | `czh_` 前缀 + 下划线（snake_case） | `czh_admin`、`czh_auth_config` |
| 数据库字段 | **驼峰命名**（与 Java 实体字段同名） | `adminId`、`userName`、`failNumTime` |
| Mapper.xml | 与 Mapper 同包 `dao/xml/` | `AdminDao.xml` |

> **重要约定**：MyBatis-Plus 已配置 `map-underscore-to-camel-case: false`，且数据库字段本身就使用驼峰（如 `adminId`），因此**实体字段与列名直接同名映射**，不要依赖下划线转驼峰；新增字段若写成下划线（如 `user_name`）将无法自动匹配。

实体类上**不写** `@TableName`，靠全局 `table-prefix: czh_` 拼接表名（`Admin` → `czh_admin`）。

## 5. 统一返回与分页

### 5.1 统一响应 `JSONResult<T>`（common 模块）

所有接口返回 `JSONResult<T>`，字段：`code / msg / data`。

```java
JSONResult.success(data);        // code=200, msg="操作成功"
JSONResult.success("提示", data);
JSONResult.success();            // 无数据成功
JSONResult.error("失败原因");     // code=500
JSONResult.permissionDenied();   // code=403 无权限
JSONResult.loginOff();           // code=401 登录失效
```

**错误码三层判据（强制，前后端唯一口径）：**

**① HTTP 状态码层：一律 200，无例外。**

`AdminAuthFailedHandler` 显式 `setStatus(SC_OK)` 后塞 401/403 是团队有意为之；原 `ErrController` 设真 404 是漏网，**已裁决统一为 HTTP 200 + body code 404**。理由：① 真 404 时前端 `if (!res.ok) throw` 先触发，**根本读不到 body**，服务端写的 `msg` 永远到不了用户眼前；② 不开口子 → 规则"HTTP 恒 200、错误看 body code"零例外；③ 部分 WAF/CDN 会替换源站 4xx 的 body。
⚠️ **在前端 FE-01 修复前，禁止引入真 4xx** —— 前端 catch 既不 resolve 也不 reject，会导致 Promise 永不 settle。

**② 业务 code 层（`JSONResult.code`）：**

| code | 含义 | 备注 |
| --- | --- | --- |
| `200` | 成功 | — |
| `400` | 参数校验失败 / 业务规则拒绝 | `MethodArgumentNotValidException`、`ConstraintViolationException`、`HttpMessageNotValidException` 等 |
| `401` | 未登录 | 由 `AdminAuthFailedHandler` 下发 |
| `403` | 无权限 | **唯一**无权限码；`888` 等自定义码已废弃 |
| `404` | 请求地址不存在 | **仅**表示地址不存在 |
| `500` | 服务异常 | 保留，带 `traceId` |

**③ 错误内容判别层：`/error` 出口不得无差别返回「请求地址不存在」。**

Filter 在 DispatcherServlet 之外执行，`@ControllerAdvice`（`commonExceptionHandler`）**抓不到** Filter 抛出的异常；全项目又无 `ErrorViewResolver` 兜底，容器转派 `/error` 后异常语义被抹平。**后果**：伪造上传 token 被拒时记录为 404 爬虫噪音而非鉴权失败，**P0 漏洞（BE-04）的利用尝试在监控中不可见**（缺陷 BE-29）。
**要求**：`ErrController` 读 `RequestDispatcher.ERROR_STATUS_CODE` 与 `ERROR_EXCEPTION` 分类返回——`ErrorException` → 原样透出 message；404 → `404`；403 → `403`；其余 → `500`。**治本：禁止在 Filter 里抛业务异常**（见 §9.2）。

`Controller` 方法返回类型统一为 `JSONResult<Xxx>`。

### 5.2 分页 `PageDto` + PageHelper

```java
// 入参：com.czh.common.dto.PageDto
public class PageDto { int page; int size; String orderBy; }

// Service 内使用
PageHelper.startPage(req.getPage(), req.getSize(), req.getOrderBy());
List<XxxVo> list = baseMapper.xxxList(req);
return new PageInfo<>(list);   // 出参类型 JSONResult<PageInfo<XxxVo>>
```

> 排序字段 `orderBy` 由前端传入，Service 内需做拼接/白名单处理（示例中对 `adminId` 做了前缀拼接），避免直接拼接未知列名引发 SQL 风险。

**插件配置位置（统一）**：`common/config/PageHelperConfig`，`admin` / `api` 共用，**启动类不再声明** `PageHelper` Bean。

```java
// common/src/main/java/com/czh/common/config/PageHelperConfig.java
@Configuration
public class PageHelperConfig {
    @Bean
    public PageHelper pageHelper() {
        PageHelper pageHelper = new PageHelper();
        Properties properties = new Properties();
        properties.setProperty("reasonable", "true");              // 分页参数合理化
        properties.setProperty("supportMethodsArguments", "true"); // 支持接口参数传分页
        properties.setProperty("returnPageInfo", "check");         // PageInfo 自动分页
        properties.setProperty("params", "count=countSql");
        pageHelper.setProperties(properties);
        return pageHelper;
    }
}
```

> `PageHelper` 实现了 MyBatis 的 `Interceptor`，注册为 Bean 后由 MyBatis 自动配置装配进 `SqlSessionFactory`，**不需要**（也不应该）手动 `new SqlSessionFactoryBean().setPlugins(...)` —— 那样只是新建了一个临时对象，不会生效。

## 6. 参数校验规范

### 6.0 请求体自动校验（默认行为，无需 `@Valid`）

`common/config/AutoValidationAspect` 拦截所有 `@RestController` / `@Controller`，对标注了 `@RequestBody` 的入参**自动执行 Bean Validation**，Controller 里**不需要写 `@Valid`**：

```java
// 推荐写法：干净，校验由切面兜底
@PostMapping("/addRole")
public JSONResult<EmptyVo> addRole(@RequestBody AddRoleDto req){
    ...
}
```

切面规则：

| 规则 | 说明 |
|---|---|
| 触发范围 | 所有 Controller 方法中带 `@RequestBody` 的参数 |
| 跳过情形 | 参数已显式标注 `@Valid` / `@Validated` —— 交给 Spring MVC 原生流程（配合方法内 `BindingResult` + `ValidateUtil.checkError`），避免重复校验 |
| 失败处理 | 取**第一条**约束违规的 `message` 抛 `RuntimeException`，由 `commonExceptionHandler` 转为 `JSONResult.error(msg)`（code 500），与 `ValidateUtil.checkError` 行为一致 |
| 级联 | 支持 DTO 内部字段上的 `@Valid` 级联校验 |
| 生效模块 | 放 common，`admin` / `api` 共用 |

> **重要影响**：此前未加 `@Valid` 的接口里，DTO 上的约束注解其实**从未生效**。切面启用后这些约束会真正开始拦截请求，需确认存量 DTO 的约束与实际业务一致（详见下方清单）。

**存量写法（保留兼容）**：已有 `@Valid` + `BindingResult` 的写法不受影响，切面会跳过，可继续使用，但新代码不必再写：

```java
@PostMapping("/addAdmin")
public JSONResult<EmptyVo> addAdmin(@RequestBody @Valid AddAdminDto req, BindingResult result){
    ValidateUtil.checkError(result);   // 校验失败抛异常，由全局处理器统一返回
    ...
}
```

**已知约束需复核**（切面启用后新生效）：

| DTO | 新生效的约束 | 关注点 |
|---|---|---|
| `AdminLoginDto` | username 6–12 位、password 6–16 位、code 4 位、uuid 非空 | **账号长度 <6 或密码长度 >16 的存量管理员将无法登录** |
| `AddRoleDto` | roleName / describe / ids 均非空 | 若前端允许备注为空提交，会被拒 |
| `EditPwdDto` | oldPwd、password 均非空 | 正常 |
| `AddSetting` | title 非空 | 正常 |
| `AddMenuDto` | name 非空 | 正常 |

> 其余 DTO（`PageDto`、`QiniuDto`、`AliOssDto`、`TxCosDto`、`SaveTosDto`、`SaveLocalDto`、`SetAuthConfigDto`、`EditXxxDto`、`GetFileListDto`、`AdminListDto`、`AdminLogDto`、`DbBackUpListDto`、`EditAvatar`）**无任何约束注解**，自动校验不会改变其行为。

```java
@Data
public class AddAdminDto {
    @Length(min = 4, max = 12, message = "账号格式错误,为4-12位")
    @NotNull @NotBlank private String userName;
    @Length(min = 6, max = 16, message = "密码格式错误,为6-16位")
    @NotNull @NotBlank private String password;
    @Min(value = 0, message = "角色ID错误") @NotNull private Integer roleId;
}
```

校验异常最终由 `commonExceptionHandler` 兜底为 `JSONResult.error(...)` 返回。

### 6.1 时间区间参数约定（stime / etime 成对出现）

**规则：请求体中的时间区间字段 `stime`（开始时间）与 `etime`（结束时间）必定同时存在、同时为空。** 即只要 `stime` 有值且非空，`etime` 就一定有值；反之亦然，不存在只传其中一个的合法情况。

因此 Mapper XML 中**只判断 `stime`**，直接用 `between ... and ...` 完成区间查询，无需对 `etime` 再单独判断一次：

```xml
<!-- 正确写法：以 stime 为触发条件，between 一次完成 -->
<if test="stime!=null and stime!=''">
    and createTime between #{stime} and #{etime}
</if>
```

不要拆成两个独立的 `>=` / `<=` 判断（冗余，且违背成对约定）：

```xml
<!-- 不推荐 -->
<if test="stime != null and stime != ''"> and createTime &gt;= #{stime} </if>
<if test="etime != null and etime != ''"> and createTime &lt;= #{etime} </if>
```

DTO 中按此约定成对声明并注明关系：

```java
@Data
public class AdminLogDto extends PageDto {
    //操作开始时间
    private String stime;
    //操作结束时间-与 stime 成对出现
    private String etime;
}
```

> 约定来源：前端时间区间选择器取值时同时赋值 `stime` / `etime`（如 `OperationLog.tsx`、`DbBackUp.tsx` 的 `times[0]` / `times[1]`），后端据此简化判断。现有 `DbBackupDao.xml`、`AdminActionLogDao.xml` 均已遵循此写法。
>
> 注意：`between` 的边界由前端保证（通常 `stime` 补 `00:00:00`、`etime` 补 `23:59:59`），后端不做二次补齐。

## 7. 安全与鉴权

基于 Spring Security + JWT，约定如下：

- **登录态**：登录成功后下发 JWT，请求经 `JWTAuthFilter` 解析；登录信息通过 `SecurityUtil.getLoginInfo(AdminDetails.class)` 在 Controller/Service 中取用。
- **统一基类**：业务 Controller 继承 `BaseController`，已注入 `RedisUtil` 及常用 `Service`（`@Lazy` 延迟注入），无需重复注入。
- **Redis 键约定**：登录态键 `adminToken_{adminId}`、角色菜单键 `roleMenus_{roleId}`。
- **退出登录**：删除 Redis 中的 `adminToken_` 键即可。

### 7.1 自定义注解

| 注解 | 位置 | 作用 |
|---|---|---|
| `@Permission(required=true, permissionList={})` | 方法 | 声明接口是否校验权限及关联权限标识；`@Permission(required=false)` 表示免校验（如登录、获取登录信息） |
| `@Log(operation="操作名")` | 方法 | 标记需要记录操作日志的接口，由 `LoggingAspect` 切面落库 |

```java
@PostMapping("/loginOut")
@Permission(required = false)
public JSONResult<EmptyVo> loginOut() { ... }

@Log(operation = "添加管理员")
public JSONResult<EmptyVo> addAdmin(...) { ... }
```

### 7.1.1 `@Permission` 判定全流程（必读）

判定逻辑全部在 `JWTAuthFilter#checkPermission`：**返回 `["admin"]` 即放行，返回空集合即 403 `permissionDenied`**。整个过程是取「候选权限串」与「角色实际拥有的权限串」的**交集**，交集非空放行。

候选权限串的构成：

```
候选集 = @Permission(permissionList = {...})  ∪  { RequestUtil.getRequestRoute() 自身路由 }
```

由此得出五条必须记住的规则：

| # | 规则 | 说明 |
|---|---|---|
| 1 | **`permissionList` 内部是「或」** | 命中任意一个即放行，不是「全都要有」 |
| 2 | **自身路由是兜底项，一定参与** | 写了 `permissionList` 不会覆盖掉自身路由，二者是并集关系 |
| 3 | **不标注 ≠ 免鉴权** | `permission == null` 时 `required` 取默认值 true，仍会校验自身路由 |
| 4 | **`@Permission(required = false)` 才真正免鉴权** | 直接放行，连角色权限表都不查 |
| 5 | **比较方式为精确相等** | `List.contains` 全等匹配，不支持通配、不支持前缀匹配 |

示例（菜单下拉接口通常开放给「能编辑菜单的人」）：

```java
// 拥有 addMenu 或 editMenu 任意其一即可访问；同时拥有自身路由 /admin/menu/getMenusByPid 也能访问
@RequestMapping("/getMenusByPid/{pid}")
@Permission(permissionList = {"/admin/menu/addMenu", "/admin/menu/editMenu"})
public JSONResult<List<GetMenusByPidVo>> getMenusByPid(...) { ... }
```

**⚠️ 首要限定：不标注 ≠ 无鉴权。** `Permission.java:11` 的 `required()` **默认为 `true`**，未标注 `@Permission` 的方法走 `JWTAuthFilter.checkPermission` 的**路由鉴权**（取 URI 前 4 段与角色权限串比对）。因此未标注的方法**全部都有鉴权**，只是依赖隐式默认。
→ **显式化的正确表述是「显式化 N 处」，不是「补 N 个安全漏洞」。**

**必须显式标注 `@Permission` 的接口类型（强制）**：删除、状态变更（冻结/解冻）、备份与还原、角色权限变更、安全配置变更、上传配置变更。高危操作还应**与 `@Log` 成对出现**（破坏性操作尤其）。

**显式化优先级（实测逐文件，按此排序执行）**：

| 优先级 | 目标 | 数量 | 理由 |
| --- | --- | --- | --- |
| **P1** | `DbBackUpController` | 6 | 破坏性操作（backup/restore/remove）全未显式标注，且已有的 3 个 `@Log` 应与之成对 |
| **P2** | `RoleController` 的 `addRole`/`editRole`/`delRole`/`roleList`；`MenuController` 的写操作 | 约 10 | 权限与安全配置变更 |
| **不做** | `LoginController`(4)、`UploadController`(1) | 5 | 有特殊放行机制（permitAll / 独立 token 校验），标了反而误导 |

> 现状逐文件：`SettingController` 映射 17/注解 9、`AdminController` 12/5、`RoleController` 6/1、`MenuController` 6/1、`CommonController` 3/2、`DbBackUpController` 6/**0**、`LoginController` 4/0、`UploadController` 1/0。**显式化任务见《现有后台改造清单》批次 F（P1/P2，本轮未执行）。**

**关于 `getRequestRoute()`（别名之所以要写全路径的原因）**：该方法取请求 URI 的**前 4 段**拼成字符串，自动剥掉路径参数，因此：

- `/admin/menu/getMenusByPid/0` → `/admin/menu/getMenusByPid`  ← 路径参数被丢掉
- 所以 `permissionList` 里的别名必须写**不带路径参数的完整四段**，写成 `"addMenu"` 或 `"/admin/menu/addMenu/{id}"` 都会静默失效
- 段数不足 4 段时按实际长度取（`Math.min(uris.length, 4)`），不会越界

**踩坑提示**：`permissionList` 里的别名是字符串硬编码，被引用的接口一旦改路径不会编译报错，只会默默失效导致全员 403。改动路由后必须全局搜索旧路径，同步更新所有 `@Permission`。

### 7.1.2 权限串与菜单表的耦合（强制 · 命名陷阱）

> 本节内容已登记为 **BE-31**（P1 · 安全 · 权限模型）。三条规则均可做成 CI 检查项。

**⚠️ 命名陷阱：`menu.route` 与 `menu.path` 的语义与字面正好相反** —— fork 出去后最容易改错数据库的一处：

| 字段 | 字面看像 | **实际存的内容** | 被谁消费 |
| --- | --- | --- | --- |
| `menu.route` | 前端路由 | **后端 API 路径**（如 `/admin/menu/addMenu`），**被直接当作权限串** | `RoleServiceImpl:104-105` 取 `menu.getRoute()` 装进角色权限集；`JWTAuthFilter#checkPermission` 与之**精确相等**比对 |
| `menu.path` | 后端路由 | **前端路由**（如 `system/role`），拼进菜单树下发给前端 | `MenuServiceImpl:112-113` 拼父子路径；前端对应 `src/Route/index.tsx` 的 key |

**判据（改库前先问这一句）**：能被 `@Permission(permissionList = {...})` 或 `getRequestRoute()` **精确相等命中**的是 `route`；能填进前端 `src/Route/index.tsx` key 的是 `path`。
旁证：`AddMenuDto:13-14` 注释（`path` 注「前端路由」、`route` 注「后端路由」）、`sql/czh_optimized.sql:115-116`（`path` 前端路由 / `route` 后端路由）。

> 推论：**`menu` 表实际被当成权限表在用** —— 一行菜单 = 一个权限点。这正是按钮级权限无法表达的根因（改造方案见《现有后台改造清单》**批次 H**）。

**⚠️ BE-32：这两个字段的命名本身不携带任何区分信息** —— `Menu.java:29-32` 的注释**中文都叫「路由」**，而 `route` 与 `path` 在英文里本就是同义词。更麻烦的是**表单层零校验**：

| 字段 | 菜单表单（`czh-admin/src/pages/system/menu/AddMenu/index.tsx`） | 校验 |
| --- | --- | --- |
| `path`（前端路由，`:145-165`） | 必填联动（`display` 依赖）+ 正则 `^[a-zA-Z0-9_-]+(\/[a-zA-Z0-9_-]+)*$` + placeholder 写明格式示例「可多段如 admin/AdminList」 | ✅ 有 |
| **`route`（后端路由，`:168-170`）** | **无 `rules`、无格式提示**，placeholder 只有「请输入后端路由」六个字 | 🔴 **零校验** |

**`route` 是全表单唯一一个零校验字段，而它恰恰是权限串的唯一来源。** 填错不会报"配置错误"，只表现为**接口 403 / 侧边栏 404**，只能靠现象反推。

**强制项：权限类字段禁止零校验（与 BE-31 配套）。** 任何**进入权限判定**的输入字段，必须有**格式约束 + 明确错误提示**。菜单表单的「后端接口路径」字段必须满足：

- **label 写明后果**：「**后端接口路径（决定权限，须与接口 URL 完全一致）**」；
- **正则校验**：必须以 `/admin/` 开头；
- **格式示例**：给出 `/admin/xxx/yyy` 的样例。

**根治（BE-32 改名）**：`Menu.path` → `frontendPath`、`Menu.route` → `apiPath`，并在术语表单列对照说明。🔴 **改名必须前后端同步**（Entity + 前端表单 + VO/DTO），**只改一侧会直接改坏菜单功能**；属破坏性变更，入《改造清单》**批次 H**。

**三条强制规则**：

| # | 规则 | 现状实测 |
| --- | --- | --- |
| 1 | **所有端点必须显式声明 `@Permission`** | 43 个受保护端点中 **25 个（58%）裸奔** —— 无注解时权限串 = 自身请求路由，必须与某条 `menu.route` **精确相等**才放行。显式化任务见《改造清单》**F-7（P1/P2，本轮待执行）**，注意是「显式化」不是「补鉴权」 |
| 2 | **`required = false` 仅限读操作** | `getUploadToken` 与 `addFile` 均免鉴权，而 **`addFile` 是写操作**（内部越权，属 BE-04 上游，非新增外部攻击面）；且 `getUploadToken` 签发的正是 `/upload` 用的 JWT |
| 3 | **权限串必须表达动作，禁止借用页面路由** | `saveQiniu` / `saveAlioss` / `saveTxcos` / `saveLocal` / `saveTos` **5 个写端点共用 1 个读串** `/admin/setting/getUploadConfig`；反向 `getAuthConfig` 挂着**写串** `setAuthConfig`。后果：**能查看上传配置 = 自动能改任意一家云存储**，且**5 家厂商无法单独授权** |

**🔴 隐形约束（新项目最常踩，当前只能靠线上报 403 反推）**：

> **新增或改名任意一个后端接口，必须同步往 `menu` 表插入（或更新）一条 `route` 相同的行，否则该接口对所有角色——包括超级管理员——返回 403。**

成因：无注解端点的权限串就是自身路由，而角色权限集全部来自 `menu.route`，`List.contains` 是精确相等 —— 表里没有这一行，交集恒空。

**模板级遗传缺陷：`getRequestRoute()` 硬截断 4 段**（曾为 `Math.min(uris.length, 4)`）：**一旦出现 5 段路由（如 `/admin/user/import/template`），第 5 段被丢弃，权限串静默放大**（`/admin/user/import/template` 与 `/admin/user/import/exec` 变成同一个权限串）。当前 48 个端点恰好都 ≤4 段，所以**它不修不会有任何现象**。

✅ **状态：已修（2026-10-14，实测通过）** —— 源码改为 `int len = uris.length;`（按实际段数全量拼接），原「最多 4 段」的**误导性注释也已一并删除并改写为警示注释**；验证载体 `RequestRouteTruncationRegressionTest` 已入库并全绿（全量 `Tests run: 53, Failures: 0`）。

⚠️ **但 fork 场景仍需自查**：**从旧版本（本次修复之前）fork 的项目照样继承这个缺陷**，源头修没修都不影响派生项目 → 一律按《新项目初始化SOP》**S8** 核对（该章为 🔒 永久条目）。

⚠️ **为什么它能一直活到现在没人觉得有问题**：该方法的注释写的是「**按实际段数截取，不足时返回已有部分**」——读起来像是已经按实际段数处理了；而实现的真实行为是「按实际段数，**但上限 4 段**」。**注释把一个安全策略（截断）包装成了实现细节（防越界）**，读者会以为那个 `4` 只是防数组越界的副作用、与权限无关，从而认为它无害。它不是被漏掉的，**是被注释"解释"成无害的**。改这条时**必须同时改注释**。

✅ **验证方式：离线可跑，无需 DB、无需启动应用**（这条正是它能在无 MySQL 环境下完成的原因）。`getRequestRoute()` 是**纯字符串函数**，只依赖 `RequestContextHolder` —— 用 `MockHttpServletRequest` 塞入 URI 即可断言（用例见《改造清单》9.5 的 `RequestRouteTruncationRegressionTest`：5 段不得截断 / 现有 ≤4 段端点行为逐字节不变 / 不足 4 段不越界）。**这条没有任何"验证不了"的前提，不得以"没有数据库环境"为由推迟。**

**CI 可检条目（建议纳入构建检查）**：

1. 扫描所有 `@RequestMapping` / `@GetMapping` / `@PostMapping` 的路由，与 `menu.route` 求**差集** → 缺行即失败（新接口漏配菜单 → 全员 403）；
2. 扫描 `@Permission(required = false)` 的方法名，命中 `add|save|edit|update|del|remove|set|upload|restore|backup` 等写动词 → 失败；
3. 扫描 `@Permission(permissionList = {...})`：同一权限串被 **>1 个写端点共用** → 告警；**读端点挂写串**（串中含 `set|save|add|edit|del`）→ 告警；
4. **权限类字段零校验 → 失败**：搜索参与 `getRolePermissions` 构造的字段（当前即 `Menu.route`），检查其**表单项是否有 `rules`**（BE-32）。

### 7.3 敏感字段脱敏（强制）

凡是要**持久化或外发**的请求体 / 返回体，必须先把敏感字段的值替换为 `****`（**字段名保留，值打码**），不允许明文落库。

> 采用「保留字段、打码取值」而非删除字段：日志结构保持一致，便于排查"这个接口当时传了什么字段"，同时不含可用明文。

**核心场景**：`@Log` 标记的接口的入参与返回值会写入 `czh_admin_action_log`（`params` / `bake` 列）。登录接口会把 `password` 与 JWT `token` 原样带进去——有日志查看权限即等同于拿到管理员密码和有效令牌。

统一使用 `SensitiveUtil.safeJson(...)`：

```java
// LoggingAspect
params = SensitiveUtil.safeJson(args[0]);                  // 入参：password → "****"
String resultJsonString = JSON.toJSONString(joinPoint.proceed());
adminActionLog.setBake(SensitiveUtil.safeJson(resultJsonString)); // 返回值：token → "****"
JSONResult result = JSON.parseObject(resultJsonString, JSONResult.class); // 回调用方用原始串
```

**匹配规则**：字段名忽略大小写，**包含**以下任一关键字即把该字段的**值替换为 `****`**（键名保留），且递归处理任意层级（`JSONObject` / `JSONArray`）：

| 关键字 | 覆盖字段 |
|---|---|
| `password` | `password`、`oldPassword`、`newPassword` |
| `pwd` | `pwd`、`oldPwd`、`newPwd` |
| `token` | `token`、`accessToken`、`refreshToken` |

效果示例：

```json
落库前：{"username":"admin","password":"zx123456"}
落库后：{"username":"admin","password":"****"}

落库前：{"code":200,"data":{"nickname":"admin","token":"eyJhbGciOi..."}}
落库后：{"code":200,"data":{"nickname":"admin","token":"****"}}
```

**约定**：
1. 新增任何含密码 / 令牌的 DTO、VO 字段，命名须能被上述关键字命中；**若命名无法命中（如 `secret`、`ak`、`sk`），必须在 `SensitiveUtil.SENSITIVE_KEYWORDS` 中补登记**。
2. 严禁为了省事直接 `JSON.toJSONString(args[0])` 落库；统一走 `SensitiveUtil.safeJson`。
3. `safeJson` 解析失败返回空串、不抛异常，不得因此绕过它。
4. 掩码统一为 `****`（`SensitiveUtil.MASK`），**不要保留原文的长度、前缀或后几位**——那会泄露信息。
5. 接口**返回给调用方的内容不受影响**，脱敏只作用于落库副本。

### 7.4 鉴权缓存与失效策略（必读）

请求鉴权链路（`JWTAuthFilter`）每个请求都要读管理员与安全配置，缓存后从 **3 次 DB** 降到 0（命中时）。

**缓存清单集中在 `common/service` 的 `com.czh.service.cache.AuthCacheKeys`**，新增缓存必须在此登记：

| key | 内容 | TTL | 失效触发 |
|---|---|---|---|
| `adminAuth:{adminId}` | 管理员鉴权视图（**不含密码**） | 60s | `AdminServiceImpl` 的 `updateById` / `update` / `removeById` |
| `authConfig:1` | 登录安全配置（全表只有一行） | 300s | `AuthConfigServiceImpl` 的 `updateById` / `update` |
| `rolePermission{roleId}` | 角色拥有的菜单路由集合 | 300s | `RoleService#updateRoleCache`（改角色时 Controller 调用）；**改菜单 route / 删菜单** 由 `MenuServiceImpl` 触发 `RoleService#evictAllRolePermissionCache` |

**三条强制约定**

1. **失效必须写在「写方法」里，不能散落在 Controller**
   `AdminServiceImpl` / `AuthConfigServiceImpl` 覆写了 MyBatis-Plus 的 `updateById` / `update`，任何调用方都无需记得手动删 key。将来新增写方法（如 `saveOrUpdate`、`updateBatchById`）**必须同步补上对等的失效逻辑**。
   TTL 只是兜底，用于覆盖"不经过 Service 的数据变更"（运维直连数据库、跑脚本刷数据）——60 秒是这类旁路修改的最迟生效时间。

2. **密码哈希不得进入 Redis**
   `AdminAuthCache` 是独立于 `Admin` 实体的窄视图。原因有二：Redis 没有账号体系，任何能连上的人都能读；而鉴权链路本来就用不到密码（签发 token 在登录阶段完成，那里走 DB 直查）。

3. **缓存对象缺字段，等于给下游埋雷**
   鉴权链路注入的 `AdminDetails` 由 `AdminAuthCache` 构造，`getPassword()` 返回 **null**。
   **校验旧密码、签发 token 这类逻辑必须回源 DB**，不得依赖 `SecurityUtil.getLoginInfo(AdminDetails.class).getPassword()`
   （`AdminController#editPwd` 已按此修正）。

**附带的三点说明**

- **`rolePermission` 的全量失效用索引集合，不用 `keys`**：`AuthCacheKeys.ROLE_PERMISSION_INDEX` 是个 Redis Set，回填缓存时 `sAdd` 登记 roleId，清理时 `setMembers` 枚举后批量删。**禁止用 `keys rolePermission*`** —— Redis 的 `keys` 是全库 O(N) 扫描，会阻塞单线程主线程。
- **`MenuServiceImpl#updateById` 只在 route 真的变化时才全量清理**：MyBatis-Plus 的 `updateById` 只更新非 null 字段，`entity.getRoute() == null` 表示本次改的是名称/排序/图标，与权限无关。
- **`JWTAuthFilter` 现在会校验 `status != 1`**：被冻结的管理员**立即失去权限**，不再能凭旧 token 操作到 Redis 里的 `adminToken_` 自然过期；`removeById` 也会删掉 `adminToken_{id}`，管理员被删除后立即下线。

## 8. 数据访问（MyBatis-Plus）

- **Mapper**：接口继承 `BaseMapper<T>`，并标注 `@Mapper`。
- **Service**：接口 + `impl` 实现继承 `ServiceImpl<Dao, Entity>`，获得 `getById / save / updateById / removeById / getOne(new QueryWrapper<>())` 等通用能力。
- **自定义 SQL**：写在 `dao/xml/*.xml`，`namespace` 指向 Mapper 全限定名；`resultMap`/`resultType` 直接映射实体或 VO。
- **全局配置**（`application-*.yaml`）：
  - `mapper-locations: classpath:com/czh/service/dao/xml/*.xml`
  - `table-prefix: czh_`
  - `logic-delete-value: 1` / `logic-not-delete-value: 0`（逻辑删除）
  - `map-underscore-to-camel-case: false`（字段名与列名同名，均为驼峰）
  - `call-setters-on-nulls: true`（null 字段也会 set，会输出到 JSON）
- **分页**：统一用 PageHelper，不混用 MyBatis-Plus 分页插件。

### 8.1 禁止 `select *`（强制）

**规则：Mapper XML 中所有查询必须显式写出需要的列名，禁止使用 `select *`。**

原因：
1. **字段漂移风险**：表新增字段（如大字段 `text`/`blob`）会被无感知地带入结果集，增加网络与内存开销；
2. **破坏 VO 契约**：`select *` 返回的列若与 VO 字段不一致，多余列被丢弃、缺失列静默为 `null`，问题难以定位；
3. **索引失效**：无法走覆盖索引，且无法通过列名快速判断 SQL 是否命中索引；
4. **可读性与评审成本**：无法从 SQL 看出该查询究竟依赖哪些字段。

正确写法（显式列名，与 `resultMap` / VO 字段一一对应）：

```xml
<!-- 正确 -->
<select id="getSettingList" resultType="com.czh.service.vo.admin.GetSettingListVo">
    select id,title,type,value,canDel from czh_setting
</select>
```

禁止写法：

```xml
<!-- 禁止 -->
<select id="getSettingList" resultType="com.czh.service.vo.admin.GetSettingListVo">
    select * from czh_setting
</select>
```

注意事项：
- 列名**必须与 `resultMap` 中声明的 `column` 完全一致**（含驼峰大小写），否则映射失败；
- 命中 MySQL 保留字的列（如 `key`、`type`、`sort`）需加反引号，例如 `` select `key`,url from czh_upload_files ``；
- 需要联表时，用表别名限定列：`select a.id,a.userName,b.roleName from ...`；
- 仅查询 VO 真正需要的列，**不需要的字段不要查出来**，避免无谓的 IO 与序列化开销。

### 8.2 禁止 N+1 查询（强制）

**规则：禁止在循环体内执行数据库查询。一次列表查询只允许对应固定次数的 SQL（理想为 1 次，联表/批量补充最多 2~3 次），不能随结果集条数线性增长。**

典型错误（N+1）：先查列表，再逐条查关联数据：

```java
// 禁止：1 次查列表 + N 次查角色 = N+1
List<Admin> admins = adminDao.selectList(null);
for (Admin admin : admins) {
    admin.setRoleName(roleDao.selectById(admin.getRoleId()).getName());
}
```

正确做法一：**批量查询 + 内存映射**（推荐，改造成本最低）：

```java
List<Admin> admins = adminDao.selectList(null);
// 收集 id 一次性批量查询
List<Integer> roleIds = admins.stream().map(Admin::getRoleId).distinct().toList();
Map<Integer, Role> roleMap = roleService.listByIds(roleIds)
        .stream().collect(Collectors.toMap(Role::getRoleId, r -> r));
// 内存中装配，SQL 总数固定为 2 条
admins.forEach(a -> a.setRoleName(roleMap.get(a.getRoleId()).getName()));
```

正确做法二：**联表 / 子查询一次取回**：

```xml
<select id="adminList" resultType="com.czh.service.vo.admin.AdminListVo">
    select a.adminId,a.userName,r.name as roleName
    from czh_admin a
    left join czh_role r on r.roleId = a.roleId
</select>
```

判定与自查方法：
- 代码中出现 `for` / `forEach` / `stream().map()` 内调用 `*Dao.*` 或 `*Service.getById/list*`，**一律视为 N+1 嫌疑**，必须重构；
- MyBatis 的 `<association>` / `<collection>` 默认也是逐条触发子查询，嵌套结果请用 `JOIN` + `resultMap` 嵌套映射，或改批量装配；
- 开发期开启 SQL 日志（打印执行耗时与条数），单接口 SQL 条数异常偏多时优先排查此项；
- 分页场景下 N+1 危害更大：每页 N 条即 N+1 次查询，列表页是最容易踩坑的位置。

**树形/递归结构同样适用此规则**（这是最容易忽视的 N+1 形态）：递归按 `pid` 逐层查子级，节点数即 SQL 次数。

```java
// 禁止：每个节点各触发一次查询，菜单越多 SQL 越多
private List<GetMenuListVo> getMenuListByPid(Integer pid) {
    List<GetMenuListVo> vos = baseMapper.getMenuListByPid(pid);
    for (GetMenuListVo vo : vos) {
        vo.setChild(getMenuListByPid(vo.getId()));   // 递归查库 → N+1
    }
    return vos;
}
```

正确做法：**一次性查出全量数据，在内存中按 `pid` 分组构建树**，SQL 固定 1 条：

```java
// 正确：1 次查全表 + 内存构树
List<GetMenuListVo> all = baseMapper.getAllMenus();          // select id,pid,name,... from czh_menu
Map<Integer, List<GetMenuListVo>> byPid =
        all.stream().collect(Collectors.groupingBy(GetMenuListVo::getPid));
List<GetMenuListVo> tree = buildTree(byPid, 0);              // 递归走内存，不再查库

private List<GetMenuListVo> buildTree(Map<Integer, List<GetMenuListVo>> byPid, int pid) {
    List<GetMenuListVo> nodes = byPid.getOrDefault(pid, List.of());
    nodes.forEach(n -> n.setChild(buildTree(byPid, n.getId())));
    return nodes;
}
```

> **补充说明**：
> - MyBatis 二级缓存、懒加载不能从根本上解决 N+1，只能掩盖问题；正确做法是**减少 SQL 次数**而非缓存单次结果。
> - Redis 缓存可以作为**兜底手段**（如菜单权限缓存 `rolePermission{roleId}`），但缓存未命中时仍会退化成 N+1，不能替代 SQL 层面的优化。
> - 已知待优化点（符合"渐进整改"原则，新代码禁止再犯）：`MenuServiceImpl.getMenuListByPid` / `getAuthMenuList`、`RoleServiceImpl.getSons` 目前为递归查库，数据量小时影响可控，但应按上述内存构树方式重构。

实体约定：

public class Admin implements Serializable {
    private static final long serialVersionUID = 1L;

## 9. 异常处理

`common/exception` 提供自定义异常与全局处理器：

| 类 | 用途 |
|---|---|
| `commonExceptionHandler`（`@ControllerAdvice`） | 全局兜底：`Exception`→`error`；`NoAuthException`→`permissionDenied`(403)；`NotLoginException`→`error` |
| `NotLoginException` | 未登录 |
| `NoAuthException` | 无权限 |
| `PasswordErrorException` / `ErrorException` | 业务异常 |

约定：业务异常继承自定义异常，由全局处理器统一转换为 `JSONResult`，**不要在 Controller 中手动 try-catch 吞掉异常**。

### 9.2 错误出口与 Filter 异常（**强制**）

**禁止在 Filter 里抛业务异常。** Filter 在 **DispatcherServlet 之外**执行，`@ControllerAdvice`（`commonExceptionHandler`）**抓不到** Filter 抛出的异常；容器会转派 `/error`，由 `ErrController` 兜底返回——**异常语义在兜底环节被抹平**。

**正确做法二选一**：

1. **Filter 只返回校验结果**，由 Controller 负责抛异常（推荐）；
2. **Filter 内直接写 JSON 响应**（`response.setStatus(SC_OK)` + 写 `JSONResult`），不再 throw。

**当前违规点**：`JWTAuthFilter`（`extends OncePerRequestFilter`）在 `:144 / :151 / :155` 三处 `throw new ErrorException(...)`（含 `checkUploadToken` 的 token 校验）。**必须先改这里，只改 `ErrController` 是治标。**
⚠️ 该问题已登记为 **BE-29（P1）**：伪造上传 token 被拒时，服务端记录为 404「请求地址不存在」而非鉴权失败 → **BE-04（P0）的利用尝试在监控里不可见**。

**`/error` 出口必须做内容判别**：见 §5.1 ③。

## 14. 开发约定速查（团队红线）

1. **业务 Controller 只放 `admin/controller/`（可自由增删改）；`framework/`（原 `baseController/`，只放 `BaseController` 与 `ErrController`）改动需评审**（见 §3）。
2. 新业务接口放 `admin/controller`（或对应业务子包），统一继承 `BaseController`。
3. **数据源只能从 `service` 模块获取**，Controller 不直接碰 DAO。
4. 入参用 `DTO`（加校验注解），出参用 `VO`，不要直接把 `Entity` 返回给前端。
5. 所有接口返回 `JSONResult<T>`，分页返回 `PageInfo<T>`。
6. 需要登录态的接口默认走 `@Permission` 校验；免校验接口显式 `@Permission(required = false)`。
7. 需审计的操作加 `@Log(operation="...")`。
8. 命名：Java 全驼峰；表名 `czh_`+下划线；**字段名驼峰**（与实体同名，不要写成下划线）。
9. 时间区间入参 `stime` / `etime` **必定成对出现**；XML 中只判断 `stime`，用 `between #{stime} and #{etime}` 查询。
10. **SQL 禁止 `select *`**：所有查询显式写列名，且列名与 `resultMap` 的 `column` 保持一致。
11. **禁止 N+1 查询**：循环内不得查库；改为批量查询 + 内存装配（`listByIds` + `Map`），或 `JOIN` 一次取回。
12. **`api` 模块（对外服务）接口必须显式声明鉴权策略**，禁止出现无鉴权的调试/测试端点（上线前需清理）。
13. **请求体 `password`、返回体 `token` 不得明文落库**：`@Log` 切面统一走 `SensitiveUtil.safeJson(...)`，敏感字段保留键名、值置为 `****`（见 7.3）。
14. **请求体强制校验**：`@RequestBody` 入参由 `AutoValidationAspect` 自动校验，**不需要** `@Valid`；参数规则一律写在 DTO 字段的约束注解上，禁止在 Controller 里手写 `if` 判空。
15. **凡参与文件路径拼接的入参必须做白名单校验**：上传接口的 `dir` 只允许 `[a-zA-Z0-9_-]+(/[a-zA-Z0-9_-]+)*`，文件扩展名只允许 `[a-zA-Z0-9]+`，禁止 `..`、绝对路径、反斜杠（见 `UploadController`），否则会造成路径穿越。
16. **CORS 必须白名单回显，禁止反射请求方 Origin**：来源白名单配置在 `czh.cors.allowed-origins`（逗号分隔），未命中不输出 CORS 头；`*` 通配时不得同时输出 `Allow-Credentials`。**且 CorsFilter 必须位于所有认证/授权逻辑之前**：通过 `httpSecurity.addFilterBefore(corsFilter, LogoutFilter.class)` 注册到 SecurityFilterChain，并用 `FilterRegistrationBean.setEnabled(false)` 禁用 Boot 的容器级自动注册。
    > **为什么不能只靠 `@Component` 自动注册**：容器级注册的默认优先级最低，排在 security chain **之后**。一旦 401/403 响应在 chain 内写出并提交（`AdminAuthFailedHandler` 直接写 `getOutputStream()`），排在其后的 CorsFilter 再 `setHeader` 已经无效——前端看到的现象是「登录接口正常，但任何需要登录的接口都报跨域」。判断方法：`curl -D - -H "Origin: http://localhost:5173" <需认证接口>`，若响应无 `Access-Control-Allow-Origin` 即为该问题。
17. **禁止直接返回 Entity**：Controller / Service 出参一律用 VO，哪怕字段与实体完全相同——目的是让接口契约可控，实体后续加字段不会自动外泄（见 8.3）。
18. **禁止把异常对象写进响应体**：未知异常对外只返回 `traceId`，堆栈写日志；业务异常（`ErrorException`）才返回可读文案（见第 9 节）。
19. **禁止 `System.out.println` / `printStackTrace`**：统一用 lombok `@Slf4j` 的 `log.info` / `log.error`，否则无法按 traceId 排查线上问题。
20. **密码编码器必须遵守 `PasswordEncoder` 契约**：`matches` 只返回 boolean，不得抛异常；"密码错误"的业务提示由 `BadCredentialsException` 链路给出。
21. **登录链路一律走 Spring Security 标准形态**：Controller 只做三件事——把入参组装成 `UsernamePasswordAuthenticationToken`（验证码等附加信息挂在 `setDetails`）、提交 `AuthenticationManager`、把 `AuthenticationException` 翻译成文案。禁止在 Controller 里 `catch` 后写失败计数、冻结之类的认证业务。
22. **认证失败原因用认证异常表达**：已有语义直接用 Spring Security 自带的（`DisabledException` 账号停用、`LockedException` 本次触发锁定、`BadCredentialsException` 凭证错误），需要自定义文案时继承 `AuthenticationException`；账号是否可用由 `UserDetails` 的布尔钩子（`isEnabled` / `isAccountNonLocked`）表达，禁止在 `UserDetailsService` 里手写 `if(status!=1) throw`。
23. **图形验证码必须真校验且一次性消费**：Redis key 必须带 TTL，比对后立即删除；禁止"生成存 Redis 但登录时不读取"（等于没有验证码）。
24. **参数校验失败必须抛 `ErrorException`**：`AutoValidationAspect`（自动校 `@RequestBody`）与 `ValidateUtil.checkError`（`@Valid` + `BindingResult` 手动校）两条路径，约束 message 本身就是给用户看的文案，必须抛业务异常；抛裸 `RuntimeException` 会被 `commonExceptionHandler` 兜底分支吞成 `服务异常,traceId=xxx`，前端拿不到可读提示。**登录类接口不要复用"创建时"的字段强度规则**（如密码 `@Length(min,max)`），只保留非空与长度上限，否则会锁死既有账号。
25. **鉴权缓存的失效写在「写方法」里**：MyBatis-Plus 的 `updateById` / `update` 在涉及鉴权数据的 Service 中被覆写以清空缓存，调用方不得也不需要手动删 key；key 前缀与 TTL 统一登记在 `com.czh.service.cache.AuthCacheKeys`（见 7.4）。**新增写方法必须同步补失效逻辑。**
26. **密码哈希不得写入 Redis**：鉴权缓存只用 `AdminAuthCache`（不含 password）；因此请求链路上的 `AdminDetails.getPassword()` 为 null，**校验旧密码必须回源 DB**。
27. **核心逻辑必须有单测**：鉴权判定、脱敏、参数校验、高风险写操作四类覆盖率 ≥ 70%；CI 必须开 `skipTests=false`（见 §16）。
28. **签名密钥必须独立**：不得把密码哈希等其他敏感数据当签名密钥用（BE-06 教训：管理员令牌用 `czh.admin-token.secret`、上传令牌用 `czh.upload-token.secret`，默认值配置在 application.yaml，环境变量可覆盖同名配置项）；模板密钥/密码**默认明文入库、开箱即用**（2026-10-15 用户决策，放弃 `.env.example` 模式）；新增部署域名必须同步 CORS 白名单（见 §17）。
29. **高风险写操作必须显式 `@Permission`**，别名写完整四段全路径；改路由后必须全局同步旧路径（见 §7.1）。**注意：这是「显式化」，不是「补鉴权」** —— 未标注的方法走路由鉴权，本来就有鉴权。
30. **仓库根目录禁止存在第二个前端工程源码副本**，历史版本用 git 分支/独立仓库管理，不靠 `-back` 目录名备份。（原 `czh-admin-back/` 294 MB 已于 2026-10-15 彻底删除，未提交改动已导出 patch 留底。）
31. **禁止在 Filter 里抛业务异常**：`@ControllerAdvice` 抓不到，异常语义会被 `/error` 兜底抹平（安全后果见 BE-29）。Filter 只返回校验结果或自行写 JSON 响应（见 §9.2）。
32. **新增或改名后端接口必须同步 `menu` 表**：插入/更新一条 `route` 完全相同的行，否则该接口**对所有角色（含超级管理员）返回 403**（见 §7.1.2）。
33. **所有端点必须显式声明 `@Permission`**；**权限串必须表达动作、禁止借用页面路由**，多个写端点不得共用同一个读串（反例：5 个 `save*` 共用 `getUploadConfig`；BE-31，见 §7.1.2）。
34. **`@Permission(required = false)` 只允许用于读操作**：写操作免鉴权即内部越权。现状 `addFile`（写）免鉴权，**本轮不做**，入《改造清单》批次 H；**前置条件：必须先确认 `menu` 表存在对应 `route` 行，否则上传功能全量 403**（见 §7.1.2）。
35. **权限类输入字段禁止零校验**：任何进入权限判定的字段必须有**格式约束 + 明确错误提示**，label 须写明后果（如「后端接口路径（决定权限，须与接口 URL 完全一致）」）。现状 `menu.route` 是全菜单表单唯一零校验字段，而它是权限串的唯一来源（BE-32，见 §7.1.2）。

## 15. 专家提示（生产环境风险与改进建议）

> 以下为 Senior Java 视角对当前工程的体检，非强制规范，供演进参考。

1. **Fastjson 1.2.83 已停止维护且历史漏洞多**：工程已引入 Jackson，建议新代码统一用 Jackson，`common` 中 `fastjson` 仅作兼容保留，避免 `autotype` 类风险。

3. **`call-setters-on-nulls: true`**：会让 null 字段进入 JSON。若希望前端区分“无值”与“未返回”，需评估此开关。

5. **构建跳过测试**：`skipTests=true` 便于出包，但建议 CI 流水线单独跑测试，保证质量门禁。
6. **密码与鉴权**：BCrypt + JWT 方案合理；注意 JWT 过期与 Redis 令牌吊销的协同（当前退出登录仅删 Redis 键，JWT 本身短期有效，需确认时效满足安全诉求）。
7. **多存储 SDK 体积**：`common` 同时依赖阿里/七牛/腾讯/火山 OSS SDK，若部分用不到，建议按部署环境做依赖瘦身或抽成可选 starter。

## 19. 数据库（DDL）规范（原《SQL规范审查报告》结论）

> 本节是建表/改表必须遵守的 DDL 约定，由原《SQL规范审查报告》（对 `sql/czh.sql` 的一次性审查）提炼为长期规范。

### 19.1 建表约定（新表必须遵守）

1. **引擎一律 InnoDB** —— 历史 8/10 表为 MyISAM（不支持事务、只有表级锁、崩溃无法自动恢复），已出 ALTER 脚本整改；
2. **字符集统一 `utf8mb4` + `utf8mb4_0900_ai_ci`** —— 历史曾 latin1 / utf8mb3 / utf8mb4 三种并存：latin1 列存中文即乱码；utf8mb3 已废弃；混查触发 `Illegal mix of collations` 并导致索引失效；
3. **高频查询字段必须建索引**，参照 Mapper XML 实际查询条件；账号类字段建唯一索引（先确认存量无重复）；
4. **索引名与列名保持一致**；最左前缀被复合索引覆盖的单列索引属冗余，不要建；
5. **字段长度与 DTO 约束对齐**（教训：`userName varchar(11)` 与 `@Length(max=12)` 不一致 → 严格模式报错、非严格模式静默截断）；
6. **创建时间用 `datetime NOT NULL DEFAULT CURRENT_TIMESTAMP`**；需要更新时间时单独加 `utime ... ON UPDATE CURRENT_TIMESTAMP`，不要把两个语义塞进一个字段（教训：`czh_upload_files.atime` 插入时为 NULL，创建时间全丢）；
7. **变长内容用 `varchar`，不用 `char`**（定长补空格且有 trailing-space 语义差异）；文件大小用 `bigint`；
8. **避免保留字作列名**（`key`、`describe`、`type`、`sort`）；存量保留字列所有 SQL 必须加反引号；
9. 表与字段必须写 `COMMENT`；
10. **逻辑删除二选一**：要么给表加 `deleted` 字段 + 实体 `@TableLogic`，要么从 yaml 移除 `logic-delete-value` 配置 —— 现状是"配置了但无字段"的空转状态，易误导。

### 19.2 脚本使用纪律（强制）

| 场景 | 使用文件 |
| --- | --- |
| 全新环境初始化 | `sql/czh_optimized.sql`（`CREATE TABLE IF NOT EXISTS`） |
| 已有数据的库变更 | `sql/线上变更脚本.sql`（ALTER，不丢数据） |
| `sql/czh.sql` | 🔴 mysqldump 归档产物（含 `DROP TABLE` / dump 残留 `AUTO_INCREMENT` / `LOCK TABLES`），**禁止当初始化脚本执行** |

⚠️ 不要把 `czh_optimized.sql` 拿到线上执行 —— 表已存在时建表语句全被跳过、修复不生效，文件末尾的 INSERT 反而可能写入错误初始值。

**线上变更顺序**：备份 → 只读检查（重名账号、NULL 时间、latin1 列是否含中文）→ 清理日志明文 → 引擎转换（低峰，锁表重建）→ 字符集统一（低峰）→ 字段类型修正 → 最后加索引（避免被前面的重建反复重写）→ 验证（引擎/字符集/索引/行数/EXPLAIN）。

### 19.3 已知设计权衡

`czh_role.ids` 以 JSON 数组文本存菜单权限（反范式）：无法 SQL 关联统计，依赖应用层解析。当前数据量小且有 Redis 缓存可接受；若需按菜单反查角色或做权限审计，再拆关联表 `czh_role_menu(roleId, menuId)`。

## 20. 经验总结与避坑（服务端，原《经验总结与避坑指南》）

> §1~§17 写「应该怎么做」；本章写「不这么做会怎样、为什么会踩、怎么查」。所有坑均来自对本仓库的真实阅读与实测。前端侧的坑见《后台开发规范》§20。

### 坑 1：照抄旧文档里的端口 → 联调不通

**现象**：前端起不来 / 接口 404 / 连接被拒。**根因**：旧文档写后端端口 8081，但 8081 是 `admin` 的 **test** 端口，dev 实为 **18081**（见 §1 端口表）；`api` 的 test 与 prod 同为 8081 撞车。**规避**：fork 后第一步核对 `application-dev.yaml` 的 `port` 与前端 `.env.development` 的 `VITE_API_URL`；改端口必须同时改 `czh.cors.allowed-origins`。**自查**：`grep -n "port:" admin/src/main/resources/application-*.yaml`。

### 坑 2：本地预览时"莫名登录失效"

**现象**：本地跑构建产物预览，登录一会儿就掉线。**根因**：`dist` 的 `.env.production` 指向远端生产库，token 被并发登录顶掉。**规避**：本地联调走 `/devapi → 127.0.0.1:18081` 同源代理；**测完必须还原 `.env.production` 并重新 build**。

### 坑 3：登录接口正常，但登录后任何接口都报跨域

**根因**（两个都可能）：① `czh.cors.allowed-origins` 未登记当前来源，预检被 OPTIONS 403 拦死；② `CorsFilter` 排在 Security 链之后，401/403 已提交响应再 `setHeader` 无效。**规避**：新增部署域名必须登记白名单；`CorsFilter` 必须 `addFilterBefore(corsFilter, LogoutFilter.class)` 注册进 SecurityFilterChain，并禁用容器级自动注册（红线 16）。**自查**：`curl -D - -H "Origin: http://x" <需认证接口>`，响应无 `Access-Control-Allow-Origin` 即为该问题。

### 坑 11：新加的接口谁都调不通，连超级管理员都 403（隐形约束）

**根因**：无注解端点的权限串 = 自身请求路由，角色权限串全部来自 `menu.route`，`List.contains` 精确相等 → `menu` 表缺行即**全员 403**。代码无提示、不编译报错、启动不告警，只能靠 403 反推。**规避（强制二选一）**：(a) 显式 `@Permission(permissionList={...})`；(b) `menu` 表插入 `route` 相同的行。**自查**：把所有 `@RequestMapping` 路由与 `menu.route` 求差集。

### 坑 12：照着字段名改数据库，把前端路由写进了权限列（命名陷阱，BE-32）

**根因**：`menu.route` 存**后端 API 路径**（被当权限串）、`menu.path` 存**前端路由**，语义与字面**正好相反**；且 `route` 是全菜单表单唯一零校验字段，却是权限串唯一来源 —— 填错只表现为接口 403 / 侧边栏 404。**判据**：能被 `@Permission` 或 `getRequestRoute()` 精确相等命中的是 `route`；能填进前端 `src/Route/index.tsx` key 的是 `path`。

### 补充：改路由后全员 403

`@Permission(permissionList={...})` 的别名是字符串硬编码，被引用接口改路径**不会编译报错**，只静默失效。改路由后必须全局搜索旧路径，同步更新所有 `@Permission`。

### 20.1 性能红线（服务端）

1. **禁止 `select *`**（含 `别名.*`）—— 必须显式列名，与 `resultMap` 的 `column` 完全一致（§8.1）。历史教训：`AdminDao.xml` 的 `select a.*,b.roleName` 曾因形如 `a.*` 被漏扫；
2. **禁止 N+1**（含**递归按 pid 逐层查库建树** —— 最易忽视的形态），一次列表查询 SQL 条数固定 ≤ 3（§8.2）。已知待改：`MenuServiceImpl.getMenuListByPid` / `getAuthMenuList`、`RoleServiceImpl.getSons`；
3. **禁止 `keys rolePermission*`** —— Redis `keys` 是全库 O(N) 扫描阻塞单线程，用 `ROLE_PERMISSION_INDEX` 索引集合枚举（§7.4）；
4. **鉴权缓存必须命中**：链路每请求 3 次 DB → 命中后 0 次；新增缓存必须在 `AuthCacheKeys` 登记；
5. **索引**：实测曾缺失 6 处（`czh_admin.userName/roleId`、`czh_menu.pid`、`czh_upload_files.pid`、`czh_area.pid`、`czh_db_backup.atime`），新表建索引是硬要求（§19.1）。

### 20.2 安全红线

1. **敏感字段脱敏落库**：`password`/`pwd`/`token` 值一律置 `****`，保留键名、不留长度与前后缀；新敏感字段必须在 `SensitiveUtil.SENSITIVE_KEYWORDS` 登记（§7.3）；
2. **密码哈希不得进 Redis**：鉴权缓存只用 `AdminAuthCache`；请求链路上 `AdminDetails.getPassword()` 为 null，校验旧密码必须回源 DB（§7.4）；
3. **路径穿越白名单**：上传 `dir` 只允许 `[a-zA-Z0-9_-]+(/[a-zA-Z0-9_-]+)*`，扩展名只允许 `[a-zA-Z0-9]+`。⚠️ 实测 4 家云存储分支没有扩展名白名单，白名单只在本地分支（BE-07 遗留）；
4. **CORS 白名单回显，禁止反射 Origin**；`*` 与 `Allow-Credentials` 不得同用（红线 16）；
5. **签名密钥必须独立**（BE-06）：管理员令牌与上传令牌各自独立配置项，不得复用密码哈希；
6. **`/admin/login/*` 整体放行过宽**（健壮性项）：应改为逐个方法放行（`login`/`getCaptcha`/`getSystemName`/`loginOut`）；
7. **禁止在 Filter 里抛业务异常**（BE-29）：异常被 `/error` 抹平成 404，会让安全攻击的利用尝试在监控里不可见（§9.2）；
8. 前端侧安全红线见《后台开发规范》§15。

### 20.3 前后端联调约定（契约速查）

| 项 | 约定 |
| --- | --- |
| HTTP 状态码层 | **一律 200**。前端 `request.ts` 依赖此前提；FE-01 修好前禁止引入真 4xx |
| 业务 code 层 | `200` 成功 / `400` 参数或业务拒绝 / `401` 未登录 / `403` 无权限（唯一） / `404` 地址不存在 / `500` 服务异常（带 traceId）。前端只看 `res.code` |
| 分页入参 | `PageDto { page, size, orderBy? }`；`size` 上限 500 |
| 分页出参 | `PageInfo<T> { list, total }` |
| 时间区间 | `stime`/`etime` 必定成对；XML 只判 `stime`，`between #{stime} and #{etime}`；边界由前端补 `00:00:00`/`23:59:59` |
| 排序 | `orderBy` 由 CZHTable 生成，前端不拼接；服务端必须白名单映射后拼接 |
| 字段 | 一律小驼峰；后端禁止直接返回 Entity |
| 认证 | token 写 `localStorage.czhToken`；请求头 `token`；退出调 `logoutApi()` |
| 401 | 清 token → 跳登录页；403 轻提示不跳转 |
| 验证码 | `uuid` + `code`，一次性消费，登录失败必须重新拉取 |

**新增接口联调流程**：① 后端 DTO（带约束）+ VO（不返 Entity）+ Controller（显式 `@Permission`、写操作加 `@Log`）→ ② 前端 `api/<模块>/` 三件套 → ③ 页面 → ④ 注册 `src/Route/index.tsx` → ⑤ 后台配菜单 `path` → ⑥ **先 curl 验契约，再连前端**。

### 20.4 典型缺陷模式与识别方法

| 症状 | 可能根因 | 定位手段 |
| --- | --- | --- |
| 登录正常、登录后接口全跨域 | CORS 白名单漏登记 / CorsFilter 位置靠后 | `curl -D - -H "Origin: ..."` 看响应头 |
| 全员 403 | `@Permission` 别名硬编码失效（改路由未同步）/ `menu` 表缺 route 行 | 全局搜旧路径；路由与 menu.route 求差集 |
| 列表页慢 | N+1 / 缺索引 / 递归查库建树 | 开 SQL 日志数条数；`EXPLAIN` |
| 日志里有明文密码 | `@Log` 切面未走 `SensitiveUtil.safeJson` | 查 `czh_admin_action_log.params`/`bake` |
| 鉴权失败在日志里显示成 404 | Filter 抛异常被 `/error` 抹平（BE-29） | 查 ErrController 是否无差别返回；grep Filter 内 `throw` |
| 首屏慢、菜单越多越慢 | 菜单树递归 N+1（BE-30 已修主支，残留见 §8.2） | 数 `getLoginInfo` 的 SQL 条数 |
| 接口无报错但页面转圈不停 | 命中真 4xx → 前端 Promise 永不 settle（FE-01） | 查响应 HTTP 状态码是否非 200 |
| 按钮级权限做不出来 | 权限串 = 菜单 route，无对应菜单的权限点无法表达 | 查权限串构造处是否只取 `menu.getRoute()` |

### 20.5 常用自查命令集

> 取证方法比结论更值钱：扫描方式直接决定结论对错。

| 目的 | 正确写法 | ❌ 踩过的坑 |
| --- | --- | --- |
| 扫后端测试文件 | `find . -path "*/src/test/*" -name "*.java" -not -path "*/target/*"` | `find -name "*Test.java"` 漏掉复数 `*Tests.java` |
| 扫 Controller 映射方法 | `grep -rnE "@(RequestMapping\|PostMapping\|GetMapping)"` | 只数文件数会低估方法数 |
| 扫鉴权注解覆盖 | 上行结果与 `grep -rn "@Permission"` 相除 | 必须注明「未标注 ≠ 无鉴权」（required 默认 true） |
| 验 CORS | `curl -D - -H "Origin: http://x" <需认证接口>` | 只测登录接口（登录后接口全跨域是另一种根因） |
| 验错误码分层 | 同时看 HTTP 状态码和 body `code` | 只看其一会漏掉「HTTP 404 + body 500」类矛盾 |
| 查死变量 | 声明处 grep 后确认是否**被读取** | 只看声明存在（`roleMenus_` 教训） |

## 21. 遗留问题与架构演进建议（原《Java项目优化建议》遗留项）

> P0 三项与 P1 大部分已于 2026-10-13 修复（匿名上传、灌库接口、CORS 反射、异常处理、Entity 外泄、matches 契约、STATELESS、线程池等）。以下为**仍待处理**的遗留项与演进建议，按优先级排列，非强制规范。

### 21.1 JWT 剩余设计问题（P1，部分已缓解）

签名密钥已独立（BE-06 已修，见红线 28），但以下项维持现状、重构时注意（改密钥/验签策略会导致全部在线用户掉线，需维护窗口）：

- **有效期 30 天过长**：建议 access token 缩短，Redis TTL 与 JWT exp 对齐；
- **每请求续期无上限**：建议加绝对过期时间（如登录后最长 7 天）；
- **IP 绑定可伪造**：`X-Real-IP`/`X-Forwarded-For` 客户端可构造；建议由 Nginx 覆盖该头，或取消 IP 绑定；
- **改密后旧 token 失效**：改为独立密钥后需显式处理（改密时删除 `adminToken_{id}`）。
